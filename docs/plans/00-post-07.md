## 0. Clear the particle counter cursor — it is stale right now

**Added 2026-08-31.** Pattern 6 is dark and has been since `18:38:52` on 2026-08-30 — the CP6
verification restarted `icc26-sim-particle-counter` and left `state/cursor` pointing past the end of the
instrument's new sequence. The poll runs perfectly, re-authenticates on schedule, writes nothing,
and logs no error. **15.5 hours, and every check was green.**

That is the documented stale-cursor trap, reproduced by accident rather than on purpose. One
gesture is the whole recovery — clear this tag in Tag Explorer, and the empty cursor resets the
`last_sequence` guard for that poll too:

```
[default]icc26/site1/qc/analyzers/particle-counter-01/state/cursor
```

Expect a backlog drain immediately afterwards, and expect to miss it — **measured
2026-08-31: 414 records in a single poll**, because one poll walks every page rather than one page
per cycle. **During that drain `em.reading.occurred_at` reads hours old and nothing is wrong** —
the instrument's clock is catching up, which is why the new check below keys on `ingested_at`.

**`tasks.py health` now catches this**, which it did not on 2026-08-30. It read the simulator's
buffer depth and called a growing backlog `OK`; it never asked whether anything was landing. It
now warns when `max(ingested_at)` on `em.reading` is over 180 s old, uses the buffer depth to say
*which* failure it is, and prints the tag above. Two documents that overstated what it caught are
corrected: [`06-poll-particle-counter.md`](06-poll-particle-counter.md) open item 10 and
[`07-sample-chain.md`](07-sample-chain.md) decision 7.

> **Worth deciding, not building.** A one-click reset button on the UDT was considered and
> dropped. The recovery was never the expensive part — not knowing was — and the trap is a
> deliberate pattern-6 demo beat whose whole argument is *"the poll runs perfectly and publishes
> nothing, with every health check green."* Stage furniture next to it softens that. Revisit only
> if pattern 6's talk track (§ 3) ends up calling for a live recovery on stage.

## 1. The review queue cannot demo 07 right now

**New, found while verifying 07 on 2026-08-30. This is the first thing to look at.**

Open <http://localhost:8000> and click Approve on the first thing you see, and pattern 7's
segment fails in front of the room. Measured, not predicted:

```json
"batch_id": null,
"batch_context": null,
"batch_context_reason": "the review message carried no equipment_id"
```

**Why.** The review screen holds two populations, and only the wrong one is clickable:

| | count | reviewable? | `equipment_id` |
|---|---|---|---|
| `awaiting-analysis` — the valve opened, no analyzer result ever arrived | **292** | no | `br-201` |
| `received` — has results, can be signed | **12** | **yes** | **all 12 null** |

The twelve are from **2026-08-25**, before `migrate-08` added `lims.sample.equipment_id`, so the
review message they produce carries none — and 07 keys `bes.batch_event` on exactly that column.
`pending_samples()` orders `sample_completion` **ascending**, so those twelve sit at the *top* of
the screen. The 292 good samples below them cannot be approved at all, because a sample with no
results is the one state a signature cannot be applied to.

**The cause is not a bug.** `CELL_ANALYZER_SAMPLE_INTERVAL_S` defaults to `0` — deliberately, since
2026-08-26, so the analyzer no longer free-runs and a person types the sample id in. Nobody has typed
one since: the newest real row in `lims.sample_result` is **2026-08-26**. Everything downstream
of the analyzer has been dark for four days and nothing complained, because 292 open entries look
exactly like a busy queue.

**The fix is the rehearsal loop, and it takes about two minutes.**

| | |
|---|---|
| 1 | <http://localhost:8085> — badge `B-1042`. Copy the `sample_id` off the page |
| 2 | <http://localhost:8087> — type that id into the analyzer's sample-login screen and run it |
| 3 | <http://localhost:8000> — the entry moves to `received`. Approve it |
| 4 | **Nothing lands on `icc26/site1/qc/deviation`** — a clean sample in `GROWTH` is compliant, and since 2026-09-06 pattern 7 speaks only on a deviation. The gateway logs `... is clean; no deviation published` |
| 5 | Press **Dirty** at <http://localhost:8089>, wait ~30 s, repeat 1–3. *Now* one message lands, `violations[0].code` = `environmental_excursion`. Press **Clean** afterwards |

**Walk this end to end at least once before the talk.** It is the only path that exercises
patterns 1, 3, 4 and 7 in one gesture. **Walked in one sitting on 2026-08-31**, `S-20260831-0103`
— the first record of it in this repo, and the progress log carries what it measured. The steps have
moved to [`../end-to-end-test.md`](../end-to-end-test.md), which is where they stay when this file is
deleted; the four rows above remain because § 1 is about *why the queue blocks them*, not how to run
them.

**One decision to take:** whether the twelve stale reviewables get cleared out before the talk.
They are the first thing on the screen and the only clickable thing on it. Leaving them means
trusting yourself to scroll past twelve rows live.

> `S-EQTEST-001` (§ 6) is a thirteenth, and `S-CP4-PROBE`, `S-NULLPATH-PROBE` and `S-NOEQ-PROBE`
> are **not** — those three were transient wire probes and wrote nothing to any table.

## 4. Does the MQTT source re-subscribe after the broker drops?

**New, and the one thing 07's build could not settle.**
`EventStreamMqttSource.onStartup` subscribes each **connected** `CirrusClient` and there is no
visible re-subscribe hook on it. If the subscription does not come back on its own, then every
time the trial in § 2 lapses, **pattern 7 goes quiet with nothing in the log saying so** — the
review message still publishes, the composite simply never appears.

Five minutes to settle:

```powershell
docker restart icc26-chariot
python tasks.py health            # wait for the MQTT listener
# then approve a sample per § 1 and see whether a composite lands
```

If it does not: disabling and re-enabling the stream is the recovery, and that belongs in 07's
talk track as a pre-flight step.
